# AudioFlow Phase 1 开发规划

## 目标：完成“可持续演进的前端基础设施”搭建，而不是只把旧页面搬进 React

---

## 一、Phase 1 的定位

### 核心目标

第一阶段不是追求“功能全部上线”，而是完成以下三件事：

1. **建立可维护的前端工程骨架**
2. **完成旧页面到新架构的最小迁移**
3. **把实时链路的边界定义清楚，为 Phase 2 打基础**

### 第一阶段结束后必须达到的结果

* 项目可用 `Vite + React + TypeScript` 正常启动
* 页面结构已从单 HTML 拆成组件化结构
* i18n、样式、类型、lint、目录规范全部落位
* Canvas 容器、控制面板、状态栏等基础壳子已具备
* WebSocket / 实时音频链路先**定义接口与边界**，不要求全部打通
* 保证后续 Phase 2 可以直接接入数据流，而不是返工重搭

### 明确的非目标

第一阶段**不追求**：

* 完整实时频谱联调
* 全量参数回写服务端
* 性能优化到 60fps 稳定
* 完整测试覆盖
* 全面移动端适配
* 复杂交互动效

第一阶段本质上是：
**“搭平台 + 立规矩 + 控边界 + 最小迁移”**

---

## 二、资深前端视角下的架构原则

---

### 原则 1：React 负责 UI 壳，不负责高频音频渲染

这是这个项目最重要的架构前提。

* React 负责页面结构、面板、状态展示、配置入口
* Canvas 负责实时绘制
* 高频音频帧不走 React render 主链路
* 从第一阶段开始，就要把这个边界定死

**原因**：
一旦第一阶段把实时数据设计成“store 更新 → React 订阅 → 组件重渲染 → Canvas 更新”，后面一定返工。

---

### 原则 2：先分层，再写功能

第一阶段最重要的不是把代码搬过去，而是把职责拆开：

* `app`：应用装配
* `components`：展示层
* `stores`：状态容器
* `services`：外部系统接入
* `domain` / `utils`：纯业务计算
* `types`：协议与领域类型
* `i18n`：语言资源

这样后面无论接 WebSocket、换协议、加新图表，都不会再把逻辑糊回 UI。

---

### 原则 3：先定义“长期稳定接口”，再逐步填实现

第一阶段里，很多模块可以先提供接口和 stub，不要求一步做满。

例如：

* `websocketService`：先定义 connect / disconnect / subscribe / send
* `audioRuntimeStore`：先定义数据结构和读写入口
* `SpectrumCanvas`：先提供 canvas mount 和 renderer 初始化壳子
* `settingsStore`：先保证本地联动和类型闭环

这是大厂常见做法：
**先定 contract，再补 implementation。**

---

### 原则 4：第一阶段就建立工程约束

不是等代码多了再补。

必须一开始就落：

* TypeScript strict
* ESLint
* Prettier
* import alias
* 命名规范
* 目录约束
* 环境变量管理
* 错误边界基本方案

否则第二阶段数据流一进来，规范就补不动了。

### 为什么这样拆

这里我建议你把原来计划中的 `audioStore.ts` 暂时不放进第一阶段主路径。
因为第一阶段要先避免一个误区：**把高频实时数据过早做成 React store 驱动。**

所以第一阶段建议：

* React store 只管低频状态
* 高频音频运行时先放在 `services/audio/audioRuntime.ts`
* 到 Phase 2 再根据实际链路决定是否桥接到 store

## 2. 状态分层设计

### A. React 可订阅状态

这些适合放 Zustand：

#### `uiStore`

* 当前语言
* 是否 loading
* 是否显示错误提示
* 当前主题（如果要预留）

#### `connectionStore`

* disconnected
* connecting
* connected
* reconnecting
* error

#### `settingsStore`

* smoothing
* attack
* decay
* weighting
* 其他 UI 参数

这些都是低频变更，适合 React 订阅。

---

### B. 高频运行时状态

这些**不要在 Phase 1 就设计成 React 驱动状态**：

* magnitudes
* fft bins
* frame timestamp
* 原始 buffer
* 渲染帧 version

这些先放进：

```text id="6x0e6k"
services/audio/audioRuntime.ts
```

由它提供：

* `getSnapshot()`
* `updateFrame()`
* `reset()`
* `subscribe()`（可选）

这样 Phase 2 接入 WebSocket 时就不会被 React 结构绑死。

## 3. 服务层设计

---

### `websocketService.ts`

第一阶段先把“协议接入层”外壳搭出来，哪怕还不真正连生产服务。

#### 职责

* connect
* disconnect
* reconnect
* 心跳预留
* send message
* on message
* on status change

#### 要求

* 不依赖 React
* 不直接操作 DOM
* 不直接 setState 到组件
* 通过回调/事件把变化抛出去

#### 推荐接口

```ts id="v5dv37"
interface WebSocketService {
  connect(): void;
  disconnect(): void;
  send(data: unknown): void;
  subscribe(event: 'message' | 'status' | 'error', listener: (...args: any[]) => void): () => void;
  getStatus(): ConnectionStatus;
}
```

第一阶段只需要把这个 contract 定出来，并接一个 mock 实现也可以。

---

### `audioProcessor.ts`

第一阶段就要把纯计算逻辑独立出来。

#### 职责

* 协议数据解析
* dB 计算
* smoothing / attack / decay 预留
* FFT bins 到绘图数据的映射预留

#### 要求

* 纯函数优先
* 可单测
* 不依赖 React
* 不依赖浏览器 DOM

这会是后面性能优化和测试的核心模块。

---

## 4. Canvas 层设计

---

### `SpectrumCanvas.tsx`

第一阶段只做三件事：

1. 创建 canvas 节点
2. 响应尺寸变化
3. 初始化 renderer 生命周期

先不要把真实高频渲染逻辑塞进来。

#### 推荐职责划分

* `SpectrumCanvas.tsx`：React 壳
* `renderer.ts` 或 `useSpectrumRenderer.ts`：命令式绘制控制器
* `audioRuntime`：提供最新数据快照

#### 第一阶段可接受结果

* 可以绘制 mock 数据
* 页面 resize 后能自适应
* 清晰支持后续接真实数据
* 销毁时正确 cleanup

---

## 5. i18n 设计

第一阶段要做，但要控制复杂度。

### 要求

* 完成 `zh / en / ja` 三语言最小接入
* 建立 key 命名规范
* 所有 UI 文本不允许继续硬编码在组件内部
* 默认语言 / fallback 逻辑明确

### key 命名建议

```json id="0l4u7z"
{
  "app.title": "AudioFlow",
  "status.connected": "Connected",
  "status.disconnected": "Disconnected",
  "controls.smoothing": "Smoothing",
  "controls.attack": "Attack"
}
```

### 不建议

* 第一阶段就做 namespace 过度拆分
* 第一阶段就上动态语言包懒加载优化
* 第一阶段为少量文案设计过重体系

---

## 6. 样式架构

建议第一阶段采用：

* `globals.css`：全局基础样式
* `theme.css`：颜色 / spacing / typography token
* `CSS Modules`：组件局部样式

### 为什么不用 CSS-in-JS

这个项目是工具型、偏实时、偏工程，不需要增加运行时样式成本。
CSS Modules 足够稳，维护成本也低。

### 第一阶段必须完成的样式目标

* 基础布局稳定
* 组件样式隔离
* 支持后续主题扩展
* 不追求视觉精修

## 模块 E：服务层外壳与 Mock 数据

### 任务

* 建立 `websocketService` 接口
* 提供 mock 实现
* 建立 `audioRuntime` 占位实现
* 建立 `audioProcessor` 的函数签名与骨架
* 设计 message type

### 为什么第一阶段要做 mock

因为前端架构阶段最怕被真实服务端联调阻塞。
先用 mock 把页面、状态、组件、Canvas 生命周期跑通，Phase 2 再接真实数据。

### 验收标准

* 在没有真实 WebSocket 的情况下，页面仍能展示“模拟连接 + 模拟频谱”
* 服务层可独立替换
* React 页面不感知 mock / real 的差异

### 验收标准

## 七、第一阶段技术决策清单

这部分是 Tech Lead 一定要先拍板的内容。

### 决策 1：高频音频帧不进入 React 主渲染路径

这是硬规则。

### 决策 2：服务层必须 React 无关

WebSocket / AudioProcessor / Runtime 不允许依赖 React。

### 决策 3：优先 mock 驱动开发，不被后端阻塞

第一阶段先保证前端架构正确。

### 决策 4：所有 UI 文案必须走 i18n key

禁止新增硬编码。

### 决策 5：先把组件边界拆对，再谈“复用”

第一阶段不做过度抽象组件库。

### 决策 6：测试先从纯函数和服务层开始，不急着铺 UI 测试

第一阶段可以只预留测试基建，不要求高覆盖。

## 八、Phase 1 结束后的风险清单

### 风险 1：旧逻辑搬迁时“只是换了写法，没有真正分层”

**缓解**：每个模块都检查是否还在直接访问 DOM / WebSocket 全局对象。

### 风险 2：过早把 magnitudes 放进 Zustand 导致后续性能问题

**缓解**：第一阶段明确只做运行时容器，不做 React 订阅式高频状态。

### 风险 3：i18n 落地不彻底，后续补起来成本高

**缓解**：第一阶段就清理硬编码文案。

### 风险 4：组件拆分过细，造成伪组件化

**缓解**：按业务边界拆，不按视觉碎片拆。

### 风险 5：为未来扩展过度设计

**缓解**：只做“可扩展接口”，不做“复杂实现”。
